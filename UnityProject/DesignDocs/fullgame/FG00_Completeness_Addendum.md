## 0. 为什么需要这份附加契约

规格列出的需求是**下限，不是上限**。过去的教训是：施工者只实现文档点名的功能，结果出现"能放建筑但不能撤销""能生产但看不出为什么停了""只在观察时正确""只有中文硬编码"这类**正常玩家一上手就撞墙**的问题。

这个游戏最终是给玩家玩的，不是为了完成任务清单。所以每个 FG Story 除了实现点名需求，还必须过一遍本文件第 4 章的**正常游戏基线清单**。规格没写、但正常玩家需要的东西，要么在本 Story 里补上，要么登记缺口并指定承接者，**禁止静默省略**。

## 2. 规格是下限

### FGR-BASE-010 下限原则
- 需求列表里的"例如""包括"都不是完整清单（沿用 IC-REQ-002）。
- 施工者必须按第 4 章基线清单逐类检查。检查到"规格没写但玩家需要"的项，按 FGR-BASE-011 处理。

### FGR-BASE-011 缺口处理
发现缺口时二选一：
- **本 Story 补齐**：缺口在本 Story 的系统范围内，并且工作量在 Story 可承受范围内，就直接补上，并写进完成报告的"补全项"。
- **登记缺口**：在 `production/design/full-game/FG-GAP-REGISTER.md` 新增一行，写清玩家症状和承接 Story。没有承接 Story 的缺口，视为本 Story 未完成。

### FGR-BASE-012 自查三问（每个 Story 标 Done 前必答）
1. 一个**第一次玩**的玩家会在本系统的哪 3 个地方卡住？各自怎么解决的？
2. 一个**玩了 30 小时**的玩家会觉得本系统哪里烦（重复操作、信息找不到、无法批量）？
3. 本系统在**后期规模**下（建筑、物品、单位数量都是 10 倍）会不会失控？

三问的回答写进完成报告。答不上来，说明还没想清楚，不能标 Done。

## 3. 自动化透明原则

### FGR-BASE-020 不做玩家没要求的事
- 机器、炮塔、常驻规则**只执行玩家显式设定的命令和规则**。禁止"智能延续"：例如自动去做下一件"看起来合理"的事、自动换目标去做玩家没要求的工作、自动改变玩家设定的优先级。
- 例外只有三种：规格明确写出的**安全行为**（例如断链进入安全模式）；**AI 教义**范围内的战斗行为；**玩家亲手设定的常驻规则**。
- 每一次由规则触发的动作，都必须能追溯到来源，在 UI 上显示为"由规则 R3 触发""由教义触发"。

> 来源：用户已三次否决"智能延续"行为。单位做了玩家没要求的事，一律当作 bug。

### FGR-BASE-021 观察不改变结果
- 家园在玩家不在场时（例如玩家在远征）也要完整运行，生产、突袭、天气的结果必须和玩家在场观察时**一致**。
- 禁止"玩家不在就走简化结算、结果不同"。确实需要降低后台运行的开销时，必须证明降级前后结果一致，并写自动测试。

## 4. 正常游戏基线清单

每个 FG Story 都要在完成报告里逐类写"适用 / 不适用（理由）/ 证据"。

| 编号 | 类别 | 必须检查的内容 |
|---|---|---|
| **B01** | 发现性 | 玩家怎么知道这个功能存在：解锁提示、引导钩子、图鉴条目、面板上的"?"帮助、tooltip |
| **B02** | 输入完整 | 键盘和鼠标都能完成；常用操作有快捷键；**所有快捷键可重绑**；右键和 Esc 取消；支持拖拽和框选的地方就要支持批量 |
| **B03** | 取消与撤销 | 放置、拆除、编辑、排队这类操作能撤销，或者能取消并全额返还；排队中的任务可以取消 |
| **B04** | 确认与防误操作 | 不可逆操作（拆除有伤亡的建筑、放弃远征、熔合消耗、覆盖存档）必须二次确认；可逆操作**不要**弹确认框打断 |
| **B05** | 状态可见 | 每个实体都有清楚的状态：工作 / 待机 / 缺料 / 缺电 / 缺流体 / 输出堵塞 / 禁用 / 损坏 / 摧毁 / 升级中，并且**不只靠颜色**区分 |
| **B06** | 原因可解释 | 任何"不能做""停了""被拒绝"都给出稳定的原因文本，并尽量给出解决办法（沿用 IC-REQ-013） |
| **B07** | 反馈三通道 | 关键事件同时有视觉、声音和文字反馈；声音有非声音的等价反馈 |
| **B08** | 通知分级与聚合 | 通知分紧急 / 警告 / 信息三级；同类通知聚合（"3 座建筑缺电"），避免刷屏；点击通知能定位到实体；有历史记录 |
| **B09** | 暂停、倍速、失焦 | 战略暂停下哪些操作可用要明确；在 0.5x 到 3x 的每一档下行为都正确；窗口失焦时按设置暂停或继续 |
| **B10** | 存读档与中断恢复 | 新增的所有状态都进存档；存档版本迁移；在任意时刻存读档都不会复制或丢失实体和物品；自动存档的时机合理 |
| **B11** | 软锁与保底 | 列出本系统可能把玩家卡死的场景（资源耗尽、死锁、全灭），并给出保底出路 |
| **B12** | 空、满、极端状态 | 空列表有空状态提示；满仓、满队列有明确提示；超大数量时 UI 仍然可用（分页、筛选、搜索） |
| **B13** | 信息与数值溯源 | 所有数值都有 tooltip；复合数值能展开来源（伤害、产量、效率的构成）；统计面板能看到趋势 |
| **B14** | 图鉴与引导钩子 | 图鉴有对应条目；新系统首次出现时**发出引导钩子事件**（"首次打开××""首次遇到××"）。引导内容本身统一在 FG15-UX-04 实现（用户决定：教学最后再做） |
| **B15** | 可访问性 | 色盲安全（颜色之外还有图标或形状）；UI 缩放；字幕；闪光和震屏可关；按住类操作可改为切换 |
| **B16** | 本地化 | 所有玩家可见文本走**文本键**，禁止硬编码字符串；中英两套文本都要能容纳（英文通常更长） |
| **B17** | 音频钩子 | 关键状态变化有音效钩子；多个同类音效有数量上限，避免叠加轰炸 |
| **B18** | 规模与性能 | 写明本系统在后期规模下的预算（见 FG15）；逐物品、逐单位的 O(N) 逻辑只能放在 `Main/Sim/` |
| **B19** | 统计与报告 | 本系统的关键产出进入统计面板和离家报告 |
| **B20** | 自动化透明 | 遵守 FGR-BASE-020 和 FGR-BASE-021 |
| **B21** | 一致性 | 快捷键、术语、图标、颜色语义与全局规范一致（见 FG13） |
| **B22** | 占位标记 | 美术、音频占位必须在 UI 或调试层明确标记，并在里程碑出口前替换（沿用 IC-REQ-014） |
| **B23** | 难度与设置影响 | 写明难度选项和游戏性设置是否影响本系统、怎么影响 |
| **B24** | 整个世界同时运行 | 镜头不在的地方（家园、前哨站、远征队、行进中的突袭），本系统是否正确；镜头飞跃、信号跳转后状态是否一致 |
| **B25** | 种子无关性 | 世界是按种子生成的（FG17）：本系统的内容不能依赖固定坐标，必须通过生成规则或手工锚点定位，并在种子测试集的任意种子下成立 |

> **关于引导**：各 FG 文档里凡是写到"第一次……时的说明 / 引导 / 演习"，施工时**只实现触发钩子**（事件和条件），引导内容统一在 FG15-UX-04 实现。

## 7. 禁止当作"完成"的情况（FG 追加）

在 AI-EXECUTION-PROTOCOL 列出的十种之外，以下情况也不算完成：
1. 只实现了规格里举的例子，没有覆盖同类的其他情况。
2. 工具只有"做"，没有"撤销 / 取消 / 拆除"。
3. UI 只有成功态，没有失败态、空状态和加载态。
4. 只在 1x 速度下测过。
5. 只在玩家观察时正确，后台运行结果不同。
6. 数值硬编码在代码里，没有入表。
7. 玩家可见文本硬编码，没有走文本键。
8. 新系统没有图鉴条目、没有 tooltip、没有引导钩子。
9. 需要控制台、调试键或编辑器操作才能完成流程。
10. 性能只在小规模下测过。
11. 快捷键写死，无法重绑。
12. 由规则或 AI 触发的动作，在 UI 上无法追溯来源。

## 8. 缺口登记格式

`production/design/full-game/FG-GAP-REGISTER.md` 每行一条：

`FG-GAP-<NNN> | 发现于（Story） | 玩家会遇到什么 | 为什么是正常游戏必需 | 承接 Story | 最迟里程碑 | 状态`

- 状态：Open / Assigned / Closed。
- 关闭时写上关闭它的 Story 和证据位置。
- 里程碑出口前，属于本里程碑的缺口必须全部 Closed，或经用户同意顺延（写明理由）。

延后的玩家可见功能，仍按 00 契约的 DEBT 格式登记（`DEBT-ID / 用户会看到什么 / 为什么当前不能完成 / 临时降级 / 承接故事 / 最迟门禁 / 自动测试`）。缺口（GAP）用于"规格漏写"，债务（DEBT）用于"已知要做但推迟"。

## 9. 人工与自动的分工

- **自动验收**负责功能正确性、错误反馈、回归、存读档、性能（沿用 IC-REQ-023）。
- **人工**只负责：好不好玩、信息负担、视觉和声音品味、数值取舍。每个里程碑的人工试玩问题见 FG16。
- 不能把"人工试玩时顺便看看功能对不对"当作功能验收。
